# Multi-Container Pods

- A multi-container Pod contains containers that are co-located, co-scheduled and managed as one Pod.

## Shared Behaviour

| Area | Behaviour |
| --- | --- |
| Lifecycle | Containers are created and deleted with the same Pod |
| Network | All containers share one Pod IP and communicate through `localhost` |
| Storage | Containers have separate filesystems but can share mounted volumes |
| Scheduling | All containers run on the same Node |
| Scaling | The entire Pod scales; containers cannot scale independently |

- Containers share the network and port space, so two containers cannot listen on the same port. A shared emptyDir survives container restarts but is deleted when the Pod is deleted.

## Types Based on Lifecycle

### 1. Co-located Containers

Regular containers defined together under `spec.containers`.

- They start after init containers complete.
- No guaranteed startup order exists between them.
- They run together for the Pod’s lifetime.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: colocated-demo
spec:
  containers:
    - name: web
      image: nginx

    - name: helper
      image: busybox
      command: ["sh", "-c", "while true; do sleep 30; done"]
```
- Use this when both containers are equally important and should run continuously.

### 2. Init Containers

Init containers perform setup work before regular containers start.

- Run sequentially, *one after another*.
- Must complete successfully.
- Do not continue running with the application.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: init-demo
spec:
  initContainers:
    - name: prepare-page
      image: busybox
      command:
        - sh
        - -c
        - echo "Prepared by init container" > /web/index.html
      volumeMounts:
        - name: web-data
          mountPath: /web

  containers:
    - name: nginx
      image: nginx
      volumeMounts:
        - name: web-data
          mountPath: /usr/share/nginx/html

  volumes:
    - name: web-data
      emptyDir: {}
```
- Regular init containers must complete before application containers begin.

### 3. Native Sidecar Containers

A native sidecar is written under initContainers with: `restartPolicy: Always`

- It starts during initialization but continues running beside the main container.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sidecar-demo
spec:
  initContainers:
    - name: log-reader
      image: busybox
      restartPolicy: Always     # must to add
      command:
        - sh
        - -c
        - tail -F /logs/app.log
      volumeMounts:
        - name: logs
          mountPath: /logs

  containers:
    - name: app
      image: busybox
      command:
        - sh
        - -c
        - |
          while true; do
            date >> /logs/app.log
            sleep 5
          done
      volumeMounts:
        - name: logs
          mountPath: /logs

  volumes:
    - name: logs
      emptyDir: {}
```
- Check the sidecar: `kubectl logs sidecar-demo -c log-reader`
- Native sidecars continue running until the application containers finish, are terminated afterward, and do not prevent a Job from completing. Native sidecars are stable from Kubernetes v1.33.

## Comparison

| Type | Starts | Stops | Main |
| ---| ---- | --- | ---- |
| Co-located container | With other regular containers | With the Pod | Another continuous application process |
| Init container | Before regular containers | After completing its task | Setup and initialization |
| Native sidecar | During initialization | After main containers | Continuous helper service |
