# Deployment Strategy

- A Deployment strategy defines how Kubernetes replaces old Pods when the Deployment’s Pod template, such as its image, changes.
- A `Deployment` triggers a rollout. A new rollout creates a new `ReplicaSet` or a New Deploy Revision.

**Kubernetes Deployments have only two built-in strategies**:

| Strategy | One-line description |
| --- | ---- |
| `RollingUpdate` | Gradually replaces old Pods with new Pods, usually without downtime |
| `Recreate` | Deletes all old Pods before creating new Pods, causing temporary downtime |

- RollingUpdate is the default strategy.

---

## Rolling Update Strategy

- A `rolling update` gradually creates new-version Pods and removes old-version Pods until all Pods run the new version.
- Kubernetes creates a new `ReplicaSet` for the new Pod template and gradually scales the new ReplicaSet up while scaling the old one down.

### Operations - Rolling Update

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 4

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

### Options - Rolling Update

| Option | Meaning |
| --- | --- |
| `maxSurge` | Maximum extra Pods allowed above the desired replica count |
| `maxUnavailable` | Maximum desired Pods allowed to be unavailable during the update |

- **Both accept a number or percentage**:
    ```yaml
    rollingUpdate:
    maxSurge: "25%"
    maxUnavailable: "25%"
    ```
    The default for both is `25%`, and they cannot both be zero.

- **Example with Four Replicas**
    ```yaml
    replicas: 4
    maxSurge: 1
    maxUnavailable: 1
    ```
    **During the Update**
    ```yaml
    Maximum total Pods:       4 + 1 = 5
    Minimum available Pods:   4 - 1 = 3
    ```

### Starting Rolling Update

```yaml
# Imperative
kubectl set image deployment/nginx-deployment nginx=nginx:1.28

# Declarative
containers:
  - name: nginx
    image: nginx:1.28
```
- A new rollout occurs when .spec.template changes. Scaling only the replica count does not create a new revision.

### Monitor the Update

```bash
kubectl rollout status deployment/nginx-deployment
kubectl get replicasets
```
- `rollout status` watches the latest rollout until it completes or fails.

## Recreate Strategy

- The Recreate strategy removes all existing Pods before creating the new-version Pods.
- Use it when old and new versions cannot run together, such as applications with incompatible database or storage behaviour. It normally causes downtime.

### Operation - Recreate

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 4

  # strategy
  strategy:
    type: Recreate

  selector:
    ...
  template:
    ...
```
- `maxSurge` and `maxUnavailable` do not apply to Recreate.

## Changing the Deployment Strategy

```yaml
kubectl edit deployment nginx-deployment

# from 
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 1

# to
strategy:
  type: Recreate
```
- Remove the `rollingUpdate` section when using `Recreate`.

## Pause and Resume a Rollout

```bash
# Pause before making several related changes.
kubectl rollout pause deployment/nginx-deployment

# Make changes.
kubectl set image deployment/nginx-deployment nginx=nginx:1.28

# Resume
kubectl rollout resume deployment/nginx-deployment
```

- Multiple changes made while paused are applied together after resuming. A paused Deployment must be resumed before it can be rolled back.

# Rollback

- A rollback returns a Deployment’s Pod template to a previously recorded revision when a new update fails or behaves incorrectly.

## Rollback Process
- Update creates a new Deployment revision.
- Check the rollout and identify failure.
- View previous revisions in rollout history.
- Rollback to the last working revision.

## Operations on Rollback

```bash
kubectl rollout history deployment/nginx-deployment

# REVISION    CHANGE-CAUSE
# 1           Initial nginx deployment
# 2           Updated nginx to 1.28

# Inspect one revision:
kubectl rollout history deployment/nginx-deployment --revision=1


# Roll Back to Previous Revision
kubectl rollout undo deployment/nginx-deployment

# Roll Back to a Specific Revision
kubectl rollout undo deployment/nginx-deployment --to-revision=1

# Verify
kubectl rollout status deployment/nginx-deployment
```

- A rollback restores the previous Deployment Pod template; it does not undo unrelated changes such as manual scaling.
