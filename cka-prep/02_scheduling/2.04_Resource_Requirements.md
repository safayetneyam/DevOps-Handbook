# Resource Requirements

- Kubernetes uses resource requests and limits to control how much CPU, memory, storage, or hardware a container receives.

## Requests and Limits

| Field      | Purpose                                                           |
| ---------- | ----------------------------------------------------------------- |
| `requests` | Minimum resource reserved; used by the scheduler to select a Node |
| `limits`   | Maximum resource the container is allowed to consume              |

The Pod’s total request or limit is normally the sum of its containers’ requests or limits.

## CPU and Memory Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: resource-demo
spec:
  containers:
    - name: nginx
      image: nginx
      resources:
        requests:
          cpu: "250m"
          memory: "128Mi"
        limits:
          cpu: "500m"
          memory: "256Mi"
```

- **Meaning**:
    ```yaml
    CPU request:    250m = 0.25 CPU core
    CPU limit:      500m = 0.50 CPU core
    Memory request: 128 MiB
    Memory limit:   256 MiB
    ```

## Behaviour of Resource Requirements

| Resource          | Request                               | When limit is exceeded                       |
| ----------------- | ------------------------------------- | -------------------------------------------- |
| CPU               | Used for scheduling and CPU weighting | Container is throttled                       |
| Memory            | Used for scheduling                   | Container may be terminated with `OOMKilled` |
| Ephemeral storage | Reserves local temporary storage      | Pod may be evicted                           |
| GPU               | Reserves a hardware device            | Cannot exceed allocated GPU count            |

CPU overuse does not normally kill the container; it causes throttling. Memory usage beyond the limit can activate the operating system’s OOM mechanism.

## Resource Units

### CPU

```
1      = 1 CPU core
500m   = 0.5 CPU
250m   = 0.25 CPU
100m   = 0.1 CPU

cpu: "500m"
```

### Memory and Storage

```
Ki = kibibytes
Mi = mebibytes
Gi = gibibytes

memory: "256Mi"
```

Do not confuse `400m` with `400Mi`; for memory or storage, `400m` means only `0.4` bytes.

### Ephemeral Storage

Temporary data includes container writable layers, logs and disk-backed `emptyDir` volumes.

```
resources:
  requests:
    ephemeral-storage: "1Gi"
  limits:
    ephemeral-storage: "2Gi"
```

If the Pod exceeds its ephemeral-storage limit, Kubernetes may evict it.

### GPU Resource

GPU resources require an appropriate device plugin.

```
resources:
  limits:
    nvidia.com/gpu: "1"
```

### Huge Pages (Optional)

Huge Pages are large memory pages provided by the Linux kernel.

```yaml
resources:
  limits:
    hugepages-4Mi: "80Mi"

# 80Mi / 4Mi = 20 Pages
```

## Important Correction

- A Pod requesting more memory or CPU than any Node can provide is not immediately OOM-killed. It remains: `Pending`
- `OOMKilled` normally occurs after a running container exceeds its memory limit.
- Check Resources:
    ```yaml
    kubectl top pod <name-of-pod>
    kubectl top pod resource-demo

    # All Pods in current namespace
    kubectl top pods

    # Usage of each container inside a Pod
    kubectl top pod resource-demo --containers
    ```
    `Metrics Server` must be installed and running; otherwise, kubectl top will not work.

## Examples

### Example 1: Container Gets OOMKilled

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: memory-demo-2
  namespace: default
spec:
  containers:
    - name: memory-demo-2-ctr
      image: polinux/stress
      resources:
        requests:
          memory: "50Mi"
        limits:
          memory: "100Mi"
      command: ["stress"]
      args: ["--vm", "1", "--vm-bytes", "250M", "--vm-hang", "1"]
```

- The scheduler reserves `50Mi`, but the container tries to use `250M`, exceeding its `100Mi` limit. Therefore, it will likely be terminated with `OOMKilled`.

### Example 2: Container Runs Normally

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: memory-demo
  namespace: default
spec:
  containers:
    - name: memory-demo-ctr
      image: polinux/stress
      resources:
        requests:
          memory: "100Mi"
        limits:
          memory: "200Mi"
      command: ["stress"]
      args: ["--vm", "1", "--vm-bytes", "150M", "--vm-hang", "1"]
```

- Creates *1 virtual-memory* worker that allocates *150 MB* and keeps that memory allocated for *1 second*.
- The scheduler looks for a Node with at least `100Mi` available. The container uses about `150M`, which remains below its `200Mi` limit, so it should run normally.
